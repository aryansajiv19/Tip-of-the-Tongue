# Architecture

## Data flow

```
Browser mic
  -> STT: Deepgram Nova-3 via the server (real word times), or the browser's Web Speech API
  -> server session: TranscriptBuffer (recent words + times) [+ voice.activity from the page]
  -> StuckDetector (pure rules; any hesitation pause is a candidate)
  -> Guesser (Claude Haiku, starts early at 300 ms of silence; JSON candidates + confidence; mock without key)
  -> Gate (confidence, self-recovery, cooldown, no repeats)
  -> web UI: pop-up with up to 3 words; AcceptanceTracker listens for the spoken word or a click
```

## WebSocket events

Defined once in `server/src/events.ts`. Times are epoch ms.

| Event                                     | Direction    | Payload                                                                         |
| ----------------------------------------- | ------------ | ------------------------------------------------------------------------------- |
| `transcript.partial` / `transcript.final` | web → server | words with start/end ms (browser STT)                                           |
| `session.brief`                           | web → server | optional meeting brief text, and the file name it came from                     |
| `session.profile`                         | web → server | "About you": name, role, the words the user often needs, and remembered words   |
| `session.settings`                        | web → server | pause wait in ms (800–5000), optional minConfidence                             |
| `session.debug`                           | web → server | turns the debug stream on or off for this connection                            |
| `guess.picked`                            | web → server | the user clicked an offered word (offer id, word)                               |
| `voice.activity`                          | web → server | `voiced`, `atMs`; sound started or stopped (changes only)                       |
| `stuck.manual`                            | web → server | the user pressed Space: suggest a word now                                      |
| `session.reset`                           | web → server | new conversation: forget transcript, offer and guess; keep brief and settings   |
| `stuck.detected`                          | server → web | reason (pause, filler, describing), context                                     |
| `guess.offered`                           | server → web | offer id, up to 3 candidates with confidence, latency                           |
| `guess.withdrawn`                         | server → web | offer id, reason (self-recovered, timeout)                                      |
| `guess.accepted` / `guess.expired`        | server → web | offer id; accepted word and time to accept                                      |
| `guesser.status`                          | server → web | `ok`; sent only when the guesser goes down or recovers                          |
| `brief.terms`                             | server → web | key terms of the loaded brief (at most 60), shown as chips                      |
| `guess.idle`                              | server → web | a confirmed stall ended with no offer (stop "finding the word")                 |
| `session.cleared`                         | server → web | answers `session.reset`; everything sent before it is from the old conversation |
| `debug`                                   | server → web | only after `session.debug`: transcript, detector, guess, gate, stt              |

## Speech-to-text

- **Deepgram** (`server/src/stt/deepgram.ts`, when `DEEPGRAM_API_KEY` is set): on connect the server sends `session.ready` with `stt: 'deepgram'`. The browser then streams raw 16 kHz mono PCM as binary frames, about 100 ms each. The server forwards them to Deepgram Nova-3 (interim results and filler words; punctuation is off, because Deepgram puts a full stop at long pauses, which would hide real stalls) and turns each result into the same `transcript.*` events the browser path uses, with real word times. Deepgram reports times from the start of the audio, and the server maps them onto its own clock, so the browser clock never matters. After 3 s without audio the stream closes, and the next chunk opens a fresh one. A dropped or unreachable connection is tried again by the next audio after 1, 2 and 4 s (audio in between is lost; a connection that opens resets the count), and a connection that goes quiet without closing is dropped after 12 s without a reply to a ping. A refused key (HTTP 401 or similar) is not retried. When the retries run out the server sends `session.ready` with `stt: 'browser'` and stops trying.

  **Keyterms.** Nova-3 can be told words to listen for (`keyterm`, repeated once per term, at most 100 terms and 500 tokens per connection; over the limit Deepgram refuses the connection, so the server stays well under, estimating tokens high: one per non-ASCII character, and at most 6,000 characters of encoded URL, since Cyrillic, Chinese and emoji terms count far more than their length suggests). The terms are the profile's personal words, then the glossary of a long brief, or for a short brief its names and jargon (capitalised words, acronyms, anything with a digit). They can only be set when a stream opens, so when the brief or the glossary changes the server closes the current stream and the next chunk of audio opens a new one with the new terms. Audio sent while the old stream is closing may be lost.

  **Speaker labels (on by default with Deepgram; `DEEPGRAM_DIARIZE=0` turns them off).** Deepgram says which voice spoke each word (`diarize=true`; streaming gives only a number, no confidence). The session takes the user to be the voice of the first words after Start (a single first word is skipped, because the first word of a new voice is often mislabelled), and corrects this from evidence: a pop-up the user accepted (spoken or clicked), or a word asked for by hand (Space), sets it to the voice of the words just before. Once it knows, a pause after another voice's words is not a stall and starts no guess; their words still go to the guesser as context. Without labels (browser speech) every voice counts as the user's. The chosen voice and the reason show in the debug stream. Deepgram numbers voices per stream, so whenever a new stream opens (after 3 s without audio, or a keyterm change) the session forgets its pick and chooses again from the first words of the new stream, assuming the user speaks first after a resume; a new conversation forgets it the same way. A voice counts as another person only after it has said three words, or when it starts after a gap of 300 ms: Deepgram sometimes gives one word in the middle of the user's speech a voice number nobody else has, and that must not hide their stall or change who the user is. A wrong first pick is only fixed by a hand ask or an accepted pop-up. Live check with two macOS voices through real Deepgram: labels were stable and right except the first word of the second voice. The scenario replay (perfect labels) is in the write-up.

  **Debug stream.** Turning on Debug in Settings (saved in the browser) sends `session.debug` on every connection, and the server then also sends `debug` events, which the page forwards to the debug view (`?view=debug`, a page or window of its own that is hidden unless opened): the raw transcript (fillers included), each change of the detector's decision, each guesser call (early or confirmed, candidates, latency, error, stale), each gate decision with its reason, and the speech-to-text mode with the current keyterms. They contain what was said, so nothing is built or sent unless asked, and the info-level server log still records only event types, never words.

- **Browser** (no key): the page runs the Web Speech API and sends `transcript.*` events itself.

## Components

- **Web speech** (`web/src/speech/results.ts`, pure): Chrome splits one hypothesis into several `results` entries and finalises short chunks, so one entry is not an utterance. On every event the web app rebuilds the whole text from all entries; the leading run of final entries is final, the rest is interim. Words keep the time they were first heard whatever the chunking. Each word is sent once as `transcript.final`, in order; the interim words are sent as `transcript.partial`. When recognition ends or restarts, the interim words are sent as a final. Open the app with `?debug=1` to record raw recognition events and download them with "Download speech trace".
- **Server-side speech (browser half)**: when the server sends `session.ready` with `stt: 'deepgram'`, Start captures the mic (`getUserMedia` with echo cancellation, noise suppression and auto gain), runs an `AudioWorklet` (`web/public/pcm-worklet.js`) that cuts 16 kHz audio into 100 ms chunks, converts them to 16-bit PCM (`audio/pcm.ts`) and sends each as a binary WebSocket frame. Web Speech is not used and the transcript comes from the server's `transcript.*` events. If the server later sends `session.ready` with `stt: 'browser'`, capture stops, Web Speech starts and a one-line notice is shown. Audio is never stored; frames are dropped if the connection falls far behind.
- **StuckDetector** (pure): takes recent words and the current time and returns `{stuck, reason, contextWindow, sinceMs}`. `sinceMs` is the end of the stall marker; words said after it may already be the answer. Text is lowercased and stripped of punctuation, so it works on plain Web Speech output. Rules, in order: (1) `pause`: silence longer than the pause setting (`STUCK_PAUSE_MS`, 1500 by default; the user can change it per connection with `session.settings`) after any word that does not clearly end a sentence. A sentence end is `.`, `?` or `!` on the word, or a closer such as "thanks" or "okay". Browser speech recognition adds no punctuation, so there every pause mid-utterance is a candidate and the Guesser must decide whether the speaker is searching for a word. Silence over 10 s is ignored. The remaining rules need at least half that silence and look only at the last 15 words said in the last 10 seconds. (2) `describing`: patterns such as "the thing you…", "the man who…", "the one that…", "the tool we use for…", "it's like a…", within the last 10 words. (3) `filler`: "the thing", "what's it called", "um/uh/er" or "you know" at the end, or a repeated "the the" at the end. (4) `describing` after a stall: a repeated determiner ("the… the") or a gap longer than the pause threshold earlier in the window, then silence once the description is finished. Saying "yes" or "sorry" after the marker cancels it. An optional `earlyMs` asks the same question after a shorter silence, for speculative guessing.
  - Known false triggers: after that short silence, ordinary phrases such as "the man who called" or "it's like a dream" still count, and so does a repaired stall that never says "yes" or "sorry"; the Guesser and Gate are expected to abstain on them.
  - Known misses: a description with no marker and no cue phrase is caught only by a pause; "you know" in the middle of a sentence is ignored.
- **Sound signals** (`web/src/audio/vad.ts`, `useVoice.ts`; `stuck/detect.ts`): the browser reads the microphone level 20 times a second and sends `voice.activity` only when the user starts or stops making sound. A change must hold 150 ms, starting needs 3x the background level and carrying on 1.8x (so it can't flap), and the background level adapts to the room. The detector then (1) rejects a word-gap pause while the user is still making sound (speech recognition lags), (2) needs the sound itself to have been silent for the pause time, and (3) treats 800 ms or more of sound with no words, followed by quiet, as a `hum` cue ("mmm", "uhhh" that speech recognition drops). A hum right after a complete sentence, or followed by a word, does not count. Without these events only words are used. Known limit: with browser speech recognition a single word held for 800 ms or more can look like a hum.
- **Asking now**: Space (focus on the page, not a field or button) sends `stuck.manual`; saying "what's the word" or "what's the word for" as the last words does the same. The server starts a guess at once (`stuck.detected` with reason `manual`), the offer cooldown does not apply, and the confidence gate still does. Ignored while an offer is showing or before anything was said.
- **Suggestion card** (`web/src/ui/`): a pure reducer (`cardState.ts`) turns server events into what the card shows: "finding the word" (shimmer, from `stuck.detected` until an offer, `guess.idle`, or 8 s), the best word with an accent underline, up to two alternatives, three confidence dots (never a percentage) and a source label when the candidate has one, then a check mark when the word is said or clicked. A suggestion fades after 6 s. Problems (microphone blocked, offline, guesser down) are one red line in the same place and never a dialog. **New conversation** sends `session.reset`; the server clears the transcript, open offer, running guess (aborted), cooldown and offer history at once and drops words still in flight from speech recognition (those ended before the reset), then answers `session.cleared`. The page ignores everything that arrives before that answer, so a late offer never shows. Settings (gear): sensitivity, microphone (used by both capture paths; the browser's own speech recognition cannot be redirected), and Debug.
- **Guesser**: sends Claude the conversation so far, the phrase where the user got stuck, the meeting brief and the profile's personal words. It returns `{candidates: [{word, confidence}], abstain}`, parsed leniently (code fences and surrounding prose are tolerated) and validated with zod: confidence is clamped to 0..1, duplicates are removed, at most 3 candidates are kept. A pasted brief can be up to 50,000 characters. A brief over 3,000 characters is not sent whole: one background Claude call extracts a glossary (at most 60 key terms, names and figures), and from then on the guesser gets the glossary plus the first 1,500 characters; until the glossary is ready, or if that call fails, it gets just the first 1,500 characters. Shorter briefs go through unchanged. What it reads: the last 1,200 words of the call (the buffer keeps 3,000) and the last 60 words as the stuck phrase, both with a "…" wherever the speaker was silent for 800 ms or more between two words (never at the end), the brief, and the profile with what each word is ("local shop Corner Mart"). The session keeps an offered word off the list for 3 minutes, and clears the cooldown if the user talks on past an offer. The reply is streamed and read only until the JSON object closes, then the rest is cancelled, so the pop-up does not wait for the end of the message. It abstains, never throws, on a timeout (`GUESS_TIMEOUT_MS`, 2500), an API error, a refusal or unparseable JSON. Provider errors and timeouts (not the model's own abstains) set `error: true` on the result; after two in a row the session sends `guesser.status` with `ok: false`, and `ok: true` on the next success. A deterministic mock runs when there is no key.
- **Gate** (pure): checks in this order. (1) The guesser abstained: silent. (2) The top word was already said since the stuck point: silent (`self-recovered`). (3) The last offer was less than the cooldown ago: silent. (4) Candidates already said since the stall marker are dropped, and so are words offered in the last 3 minutes, including longer forms of them ("onboarding team" after "onboarding"; a shorter, more exact form such as "SOC 2" after "SOC 2 report" is let through; a hand ask may repeat). (5) The best remaining word must reach `GATE_MIN_CONFIDENCE` (0.6) or the gate stays silent. Otherwise it offers up to 3 words; after the top one, only words at half the threshold or better. Spoken words are compared after lowercasing and stripping punctuation, possessives and simple plurals, so "chemist's" matches "chemist"; multi-word candidates match a run of spoken words.
- **AcceptanceTracker** (pure): only words that start after the offer count. If the user says any offered word (or phrase) within the acceptance window, the offer is accepted, with the time it took; if several are said, the earliest wins. With no match, the offer is pending until the window has passed, then it expires.
- **Session** (`server/src/session.ts`): one per WebSocket connection. It feeds transcript events into a `TranscriptBuffer` and polls every 100 ms, because a pause is silence and no event arrives when one passes. One stall triggers at most one guess: words already reacted to are not re-checked. While an offer is open, each check asks the AcceptanceTracker. A spoken candidate, or a click on one (`guess.picked`, accepted only for the open offer, one of its words, inside the accept window), sends `guess.accepted`. Six or more new words without a candidate means the user has moved on, so it sends `guess.withdrawn` (`self-recovered`). The window running out (10 s) sends `guess.expired`. After an offer, the gate's cooldown is 8 s.
  - Speculative guessing: after `SPECULATE_AFTER_MS` (300) of silence the early signal starts the guess in the background. If the user speaks again first, the result is dropped and the call aborted. When the stall is confirmed, a result already in hand is gated and offered at once; one still in flight is offered the moment it lands. The gate still uses the words said since the stall marker, so self-recovery suppresses it. The cost is one extra Claude call per pause that does not become a stall; the server logs `speculated`/`discarded` counts and `stallToOfferMs`. `SPECULATE_AFTER_MS=0` turns it off.
  - The gate is given the words said after `sinceMs` (the stall marker), not after the final silence, so a word the user has already said is never offered back.

## Overlay and desktop app

The page is a control pill (pause/resume, a five-bar mic waveform, a listening timer, the context button ("Add context", or "Meeting · <file>" once a brief is loaded), labelled keycap hints, New conversation) (420 px wide, 56 px tall; every button at least 44 by 44 px) with one calm line under it (a first-run hint until the first Start, then "Listening. I'll only speak up when you pause on a word.", plus a faint "Heard: …" of the last six words) and the suggestion card. A blocked microphone puts the pill back to play with the reason and a Retry. Debug controls exist only on a page opened with `?debug=1`. `app/` is an Electron shell around that same page: a frameless, transparent, always-on-top window at the top right of the active screen (16 px margin, re-placed when displays change), no taskbar or Dock icon, never focused when shown, and deliberately not content-protected so it appears in screenshots and screen sharing. The main process starts the server and the Vite dev server as child processes and stops them on quit, registers the global shortcuts (Cmd/Ctrl+\\ show/hide, Cmd/Ctrl+Enter manual trigger), owns the tray menu, and sizes the window to the page, up to the work area of its screen minus the margin above and below (`maxHeight` in `app/src/placement.ts`). The page and the main process talk over a small preload bridge (`window.tott`): commands in, window height and listening state out. Window placement is pure code in `app/src/placement.ts`. In a browser the page runs the same shortcuts itself.

The glass is a 0.88-opaque dark surface, not native blur: `backdrop-filter` cannot blur other apps' windows, and macOS vibrancy fills the whole window rectangle (square slab behind the rounded pill and the gap before the card), so the separate pill and card are kept and the opacity is what keeps text at 4.5:1 or better on bright backdrops (`web/src/ui/contrast.test.ts`). Esc is a global shortcut only while a suggestion is showing, since the overlay never takes focus.

## Meeting prep

A compact drawer under the pill (opened from the context button, closed by default) takes a dropped or chosen PDF, `.md` or `.txt` file. PDFs are read in the browser with pdf.js; the text (at most 50,000 characters) is sent as `session.brief` with the file name as `source`, and becomes the brief for the guesser and the key terms for speech recognition. The server answers with `brief.terms`: the names and jargon of a short brief right away, the glossary of a long one when it is ready. A suggested word that appears in the document (case-insensitive, whole word or phrase) carries the document's name as `Candidate.source`. Nothing is stored: removing the document clears the brief. The drawer is at most 400 px tall (`--drawer-max-height`) and scrolls inside, because the desktop window has a maximum height (`MAX_HEIGHT` in `app/src/placement.ts`); the pill shows "Meeting" in full and shortens the file name first.

**About you.** The same drawer has an "About you" section: a name, a role and a short list of words the user often needs (one per line or separated by commas). It is saved in the browser's localStorage (`tott.aboutYou`) and sent as `session.profile` after a short pause in typing, on every (re)connect, and whenever it changes; nothing is sent until there is something to send. The server rejects anything over 100 words per list, a word over 40 characters, a name or role over 80, or any control or line-break character (the words go into the guesser prompt). The server keeps it for the connection (it survives a new conversation) and merges it with the `PROFILE_PATH` file profile (`mergeProfiles`): the page's name and role win, and the words are added after the file's, without repeats. The merged profile is what the guesser sees ("user Dana; role product lead; often forgets ...") and its words are Deepgram keyterms inside the existing 100-term, 400-token budget, ahead of the brief's terms. **Remembered words** are the words the user accepted (by saying them or clicking), added when `guess.accepted` arrives: only the word, never what was said, newest last, at most 100 with the oldest dropped first, kept on this device. One "Forget" button clears them. They are sent with the profile (after the user's own words, so they are the first to be squeezed out of the keyterm budget), which is how an earlier meeting's words carry over without storing any conversation.

## Key decisions

- No training: prompting + rules, measured by the eval set.
- Fast model by default for latency.
- Abstaining is a valid output.

## Limits

- Tested only on our own written, scripted examples; not tested with people with aphasia. No claim of clinical benefit.
- One mic hears both sides. With Deepgram the voices are labelled and only the user's voice starts a guess; with browser speech there is no speaker separation.
- Speech-to-text may mishear real aphasic speech; accuracy on atypical speech is unknown.
- Planned, not built: a spoken cue (needs echo handling, because the mic would hear the cue and count it as the user saying the word).

## Where this could go

- Phone-call mode for people with aphasia who avoid calls (link to Hiya's call products).
- On-device STT for privacy; personal vocabulary learned over time with consent.

## Evaluation

`npm run eval -- --split dev|holdout|all --guesser mock|claude` runs the hand-written items in `data/eval/circumlocutions.json` through the real modules. Each utterance becomes timed words: 300 ms apart, with a 2000 ms pause wherever the text has "...". The runner replays the live server by calling `detectStuck` every 200 ms from the first word to 2 s after the last; "detected" means it fired at least once. Only then does the item go to the guesser (using the last trigger point, with the words heard by then) and the gate (the example profile and the item's meeting brief, if any, are passed in). Items are written by us in the documented style of circumlocution and never copied from a corpus. 11 of the 56 items (9 of the 41 stall items) are `holdout` and are never used for tuning.

- Stall items (objects, places, people, meeting terms, personal words): detector hit rate; then top-1 and top-3 (is an acceptable word first, or among the first three; a stall the detector misses counts as a miss), abstain rate, offered rate, and false-offer rate (of the offers made, the share where no offered word is acceptable).
- Fluent sentences with a thinking pause (`not_stuck_pause`, items marked `"pause": true`, added after the first evaluation as dev items): the detector fires on these by design, so the figure that matters is how often anything is offered. The target is 0.
- Silent items (`not_stuck` fluent speech, `self_recovered` where the user says the word after stalling): the share where the detector fired and the share where the app offered anyway. Any offer here is wrong.
- Latency of the guess, p50 and p95.

Results are written to `eval-results/` (gitignored). The `mock` guesser only covers a few dev items, so its numbers show the pipeline works, not how good Claude is. Spoken input, real aphasic speech and speech-to-text errors are not covered.

**Harder set and model comparison.** `data/eval/hard.json` (`--set hard`, 41 items, 10 held out; h41 was added from a miss in the live scenarios) is meant to separate models: the word follows only from earlier lines of context, targets that are verbs, adjectives or idioms, technical terms taken from a multi-paragraph brief, repeated starts written plainly, and `not_stuck_unknowable` items ("my name is…") where nothing can be known and any offer is wrong. `--model` overrides `ANTHROPIC_MODEL` for a run, so Haiku, Sonnet and Opus can be compared on accuracy, false offers and latency. The guesser turns thinking off the way each model allows (Opus cannot, so it runs at the lowest effort). Result: Haiku 5.5 stays the default. On the hard dev set Sonnet 5.5 was a few items better but not clearly (intervals overlap) and about 0.7 s slower; Opus was no better and slower still. See `docs/write-up.md`. Sonnet is a documented option via `ANTHROPIC_MODEL`; there is no model router.

**Scenario suite.** `data/eval/scenarios.json` holds 24 written two-speaker conversations of 20 to 50 lines (the last nine, s16–s24, were written before being run: a lecture Q&A, a support call, a family call, finance, a very fast speaker, two code-switching ones, a specialist appointment, and recogniser errors) (sales calls, a job interview with a company document as the brief, a doctor's appointment, standups with jargon, a client renewal with brief and profile, casual catch-ups, non-native phrasing, repeated starts, the other speaker searching for words, a word needed from far earlier in the call, and fast talk with short pauses). The user is `me`; one microphone hears both speakers, so the session gets all the words with no speaker labels. `npm run scenarios -w eval -- --split dev|holdout|all --guesser mock|claude [--model id]` plays each conversation through the real session on a virtual clock: words arrive as partial and final results (no punctuation, as a recogniser sends them), every "..." is real silence, and a guess takes its real latency on the virtual clock. Each pop-up is attributed to the line of the last word heard before it and scored: correct or wrong on a line where the user is reaching for a word, a miss if there is none, and a false pop-up on a fluent line, during a self-recovery, or on the other speaker. The report gives these per conversation type, the silence at the moment of the pop-up, the guess calls spent, and a list of every failure. 4 conversations are held out.

**Live scenarios.** `npm run scenarios:live` speaks each scenario with macOS `say` (a different voice for each person, real silence for each "..."), and streams the audio in real time as 100 ms binary frames into the real server, so it goes through real Deepgram (labels on), early guessing and Claude, with no browser. Pop-ups are mapped to lines by audio time and scored with the same scorer as the text replay; the report adds, per user voice, whether the session picked the right voice, how many words carried their speaker's usual label, and the time from the end of the last word to the pop-up. A pop-up counts for the line in progress when it appears, as in the replay. The result file also keeps the recogniser's words and the session's debug events on the audio clock. `--voices`, `--split` and `--scenario` limit the run (a run lasts as long as the audio; `--dry-run` only speaks and reports the length), and `--pause-resume` stops sending audio for 4.5 s before one of the user's lines, so Deepgram's stream closes and a new one opens. The keys come from the environment.

**Robustness.** Two flags test claims we make. `--no-context` runs the same items without the meeting brief and the profile, so comparing the work and profile categories with and without shows how much the brief and personal words help. `--stt-noise` imitates Chrome's Web Speech on the transcript: um/uh/er are dropped, text is lowercased and unpunctuated, and about 10% of non-target words are swapped for a mishearing from a small fixed table (seeded, so repeatable). Target words are never changed, and timing is kept, so pauses still happen. The realised swap rate is printed in the report. This is a rough stand-in for real recognition errors, not a measurement of them; atypical speech may be recognised worse. `npm run compare -w eval -- <a.json> <label> <b.json> <label>` prints two runs side by side (detector hit rate, top-1, false offers) per category.
