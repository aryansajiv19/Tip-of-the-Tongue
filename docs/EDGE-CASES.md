## Misses seen in the Claude eval

Two runs of the 56-item set, then a final holdout run with the shipped prompt (see `docs/write-up.md`). Only the second run recorded the words Claude offered. The data was not changed. For c30 only, a prompt line was added afterwards (see below); it was tuned on dev items.

- **c30, "the red, amber and green lights" (dev, missed in both runs).** Run 2: Claude split the two-word answer into "traffic" (0.9) and "lights" (0.4), so only "traffic" was offered. Pattern: a multi-word target comes back as separate words. We then added one prompt line, "keep multi-word names together as one candidate (e.g. 'post office')", using an example that is not in the eval set. A first version used "traffic lights", c30's own answer, and was replaced because that leaks the answer. With the clean example, c30 returned "traffic lights" as one candidate (0.85-0.9) in 3 of 3 dev reruns. This is tuned on dev, so the gain may partly be noise.
- **c36, "the list of things to do next" (dev, missed in run 1, passed in run 2).** Run 2 offered "action items" at exactly 0.6, the gate threshold. Pattern: borderline confidence, so the outcome varies between runs.
- **c18, "the warm thing with sleeves that goes over your jumper" (holdout, missed top-1 in all three runs).** Run 2: "cardigan" (0.9), "jacket" (0.5), "coat" (0.3). Claude picked a more specific item of clothing than the word we wrote; "jacket" and "coat" were still offered, so it was not a false offer. Pattern: a specific, plausible word that our acceptable list does not include. Run 1 counted it as a false offer. In the final holdout run (shipped prompt) Claude offered only "cardigan" (0.85), which is a false offer: the user would see one wrong word. No other holdout item missed.

## Findings from the ablations

- **No profile means confidently wrong.** Without the personal profile, personal words (Corner Mart, Priya, Dr Okafor) got generic guesses ("corner shop", "daughter", "GP") at 0.6-0.8 confidence, so 3 of 3 offers were wrong. The gate cannot catch this, since the model is confident. Design answer: keep the profile in the prompt; with an empty profile, expect generic, wrong offers on personal words.
- **Mishearings can bring back the multi-word split.** In one noisy dev run "traffic lights" came back as "traffic" and "lights" again. See `docs/write-up.md` for the numbers.

## Findings from the scenario suite

Whole two-speaker conversations (`data/eval/scenarios.json`), see `docs/write-up.md` for the numbers.

- **Other speaker stalls.** One microphone, no speaker separation: when the other person says "um… the thing for the…", the app can offer the user a word (3 of 45 other-speaker lines on the holdout, 1 to 2 of 152 on dev). Known main limit without speaker labels. With Deepgram's labels (on by default) the user's voice is taken from the first words after Start and only that voice starts a guess: 0 of 141 other-speaker lines in two dev replays and 0 of 42 on the holdout, with perfect labels. Deepgram numbers voices per stream, so when a new stream opens (listening paused for 3 s) the session forgets who the user is and picks again from the first words of the new stream. A wrong first pick is fixed only by a manual ask (Space); with browser speech there are no labels.
- **No punctuation means no sentence ends.** The recogniser sends plain words, so a finished sentence followed by silence looks like an unfinished phrase. The guesser has to judge it. Pauses are marked "…" between words so a description that follows a stall can be told from a finished sentence; there is deliberately no mark at the end, which made finished sentences look like searches.
- **Old words come back.** After a finished sentence the model sometimes reaches for a word offered earlier in the call. An offered word stays off the list for 3 minutes.
- **Right word, too little confidence.** About 3 per dev run (and the one holdout miss, "sun cream" 0.40) were the right word under the 0.6 gate. Kept silent on purpose.
- **A weak first guess at the bare pause.** A pop-up can appear at "I need to pop to the…" before the description. If the user talks on, the cooldown is cleared so a better guess can follow; the wrong first pop-up has already been seen.
- **Pop-up then self-recovery.** The user pauses 2 s, a pop-up appears, then they find the word: the pop-up is withdrawn. Expected, scored as a pop-up during self-recovery.
- **Very long calls.** The guesser reads the last 1,200 words (about 8 minutes) and the buffer keeps 3,000; a word needed from before that is not seen. Measured only up to a 560-word conversation.

**Not covered.** A hidden or throttled browser tab (the level meter slows down; the desktop overlay is never hidden). A real Bluetooth profile switch (only the "track ended" path is tested). A real Mac sleep (simulated with a clock jump and a suspended audio context). Real Deepgram and Anthropic outages (tests use stand-in servers). The quiet-input thresholds (0.03 RMS, 10 s) are measured guesses and need real recordings to tune. A brief in a script without capital letters gets no keyterms from a short brief (a long brief still gets the model's glossary).

## Desktop app start-up

| Situation                      | What happens                                                                                                                                                                                                        |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Launched a second time         | The running app comes forward (or shows its menu if it is still starting); no second server.                                                                                                                        |
| Server slow to start           | The tray menu shows "Starting…" at once; after 60 s it shows "Couldn't start: …" with Retry.                                                                                                                        |
| Port 47821 held by another app | Checked before the server starts: "Couldn't start: port 47821 is in use by another app". The page, which carries the token in its address, is never loaded from a port we do not hold.                              |
| Server stops                   | Started once more automatically (the page reconnects and resends brief, settings and profile); a second stop soon after shows "Couldn't start" with Retry. A server that ran 5 minutes first gets its restart back. |
| Uncaught error in the app      | Written to `userData/logs/app.log` (rotated at 1 MB, 2 old files); the app keeps running. No transcript text is logged.                                                                                             |
| Microphone refused in macOS    | A dialog explains and opens System Settings › Privacy & Security › Microphone.                                                                                                                                      |

Not covered: the failure states are tested as logic (supervisor, port check, log) but not clicked through in a packaged app.
